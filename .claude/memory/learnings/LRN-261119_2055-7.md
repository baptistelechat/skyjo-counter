# LRN-261119_2055-7 — Gain estimé par un sous-agent : le mesurer en A/B avant de garder

**Pattern observé** : l'agent mosaïque annonçait « 25-30 s → 12-15 s » sans pouvoir exécuter Mirage (Node). La mesure réelle a donné +21 % de temps, et un score faux de plus. Une estimation d'agent n'est qu'une hypothèse. Le protocole qui a marché :
- l'ancienne version dans un `git worktree --detach` à côté, avec `node_modules` partagé par jonction (`New-Item -ItemType Junction`) ;
- lancée sur un autre port via une entrée temporaire de `launch.json` ;
- onglet visible, modèle préchargé par un scan de chauffe ;
- une version après l'autre, jamais en parallèle (le CPU est partagé), sur les mêmes fixtures.

Retirer la jonction avec `rmdir` avant `git worktree remove`.

**Contexte** : vague 2 des pistes de fiabilité de Skyjo Scan.

**Application future** : toute promesse de gain de vitesse ou de fiabilité venue d'un sous-agent se vérifie en A/B réel avant d'être gardée. Deux pièges :
- un Web Worker WASM n'est **pas** ralenti dans le panneau navigateur masqué (~10 s par passe, masqué ou non) : ne pas accuser le panneau d'une lenteur réelle ;
- Vite recharge toute la page quand le lockfile change (`Re-optimizing dependencies`), ce qui efface un banc lancé dans la page : relancer après le rechargement ;
- une autre session qui scanne ou teste en même temps (autre serveur de dev, autre vitest) donne un bruit de ±2× sur le temps total (A 44 s contre B 24 s sur la même photo), même en alternant A/B puis B/A : exiger une machine calme, ou comparer `passes` et la grille plutôt que le temps.

Quand le changement est optionnel (un callback), pas besoin de worktree : l'A/B se fait dans la même page avec `const m = await import('/src/lib/moteur.ts')`, en appelant `m.scanner()` avec puis sans l'option, résultats stockés sur `window` et relus par sondage.
